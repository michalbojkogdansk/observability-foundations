Scenario 1: TimescaleDB Spike Detector

time_bucket() · z-score anomalies · hypertable scans

Z-score measures how many standard deviations a reading sits above or below its own average. Formula: z = (value − μ) / σ where μ = the mean (average over all samples) and σ = standard deviation (how spread out values typically are). Example: if avg latency is 150 ms and σ is 80 ms, a spike to 450 ms gives z = (450−150)/80 = 3.75, flagged as an anomaly. A z above 2.5 sits in the extreme 1.2% tail of the distribution. In business terms: "this spike is so unusual it would happen by chance less than 1% of the time; treat it as an incident."

Why is TimescaleDB faster on the second run? Both engines share the same PostgreSQL buffer pool (shared_buffers). On the first run, pages are read from disk. On a re-run the same pages are still in RAM, so both queries hit memory. TimescaleDB's chunk pruning means it loaded fewer pages on the cold run, giving it a head start for subsequent queries. At 200k rows the advantage is modest; at tens of millions (where chunk files are too large to cache in full) pruning dominates and the gap widens dramatically.

TimescaleDB is a PostgreSQL extension, not a separate database. Think of it as a specialised edition of PostgreSQL built from the ground up for large volumes of time-stamped data: it automatically partitions data into time-based chunks, so a 7-day query skips irrelevant partitions entirely and scans only what it needs. It speaks standard SQL but adds time_bucket(), percentile_cont(), and hypertable chunk-pruning, making anomaly detection on 100 K rows fast even on a free-tier Neon instance.

Plain Postgres:

-- Identical output to the TimescaleDB query below.
-- date_trunc() does a full index-range scan through raw rows.
SELECT date_trunc('hour', ts) AS bucket,
  metric_name,
  AVG(value)   AS avg_val,
  MAX(value)   AS max_val,
  PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY value) AS p99,
  COUNT(*)     AS samples
FROM spike_metrics
WHERE ts > NOW() - INTERVAL '24 hours'
  AND service = 'api-gateway'
GROUP BY bucket, metric_name
ORDER BY bucket DESC, metric_name;

-- Adding z-score costs nothing: window runs on ~72 already-grouped rows:
-- WITH hourly AS (... above ...)
-- SELECT *,

--     / NULLIF(STDDEV(avg_val) OVER (PARTITION BY metric_name), 0) AS z_score

TimescaleDB (hypertable with chunk exclusion):

-- Same output as above. time_bucket() tells the query planner which
-- daily partition files overlap the window; all others are skipped
-- entirely before any row is read. Gap widens at millions of rows.
SELECT time_bucket('1 hour', ts) AS bucket,
  metric_name,
  AVG(value)   AS avg_val,
  MAX(value)   AS max_val,
  PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY value) AS p99,
  COUNT(*)     AS samples
FROM spike_metrics
WHERE ts > NOW() - INTERVAL '24 hours'
  AND service = 'api-gateway'
GROUP BY bucket, metric_name
ORDER BY bucket DESC, metric_name;

Scenario 3: OpenTelemetry Trace Explorer

✓ Live, tracing to Grafana Cloud

Click the button and one request runs through three real hops: a Neon query, a z-score anomaly pass in Python, and a Redis cache check, instrumented end-to-end with the OpenTelemetry SDK. Each request gets a trace ID that opens directly in Grafana Tempo, broken down span by span so you can see exactly which hop cost the time.

Scenarios 1 and 2 taught you to detect that something is wrong. This one teaches the next step: once you know a request is slow, a trace tells you where: not "the API is slow," but "94% of this specific request's time sat in one Postgres query." That's the difference between a metrics dashboard, which tells you something's off, and a trace, which tells you what to fix first. It's the same instinct that separates guessing at root cause from actually finding it during an incident.
